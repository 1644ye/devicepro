## 官方配置中的设备身份

`config/DeviceData/ZEN65/Config.json` 是 AES-256-CBC 配置，不是可直接读取的 JSON。静态分析 `RgCommon.dll` 的 `RgCryptFile::DecryptFileData`，确认使用 OpenSSL `EVP_aes_256_cbc`、嵌入的固定配置密钥和 IV；使用 .NET AES 解密副本，成功得到可解析的完整设备定义。复现脚本：`research/zen65-local/decrypt-config.ps1`，结果：`Config.decrypted.json`。没有加载或调用官方 DLL。

`Set24GDevcie(bool)` 会将数据块大小设为无线 0x18 / 有线 0x38；`Is24GDevice` 在两个 CHidMessage 连接对象之间选择。此证据与上述 DeviceType 1 / 2 的区分相符。

**此安装版配置没有 3554:FA09 或 36B0:3002。** 后续经用户拔插前后的 PnP 差异，已确认本机这把 ZEN65 的 2.4 GHz 接收器为 **36B0:3002，serial 19971217**；3554:FA09 为其他设备。这个结论只针对本机这把键盘，不能把品牌共用 VID/PID 普遍套用到所有 ZEN65。实际接收器 FF00:0001 为 Report ID 3F、payload 63；原生驱动逻辑帧为 AA 开头的完整 64 字节，尚无证据支持把 AA 替换为 3F 或缩短帧发送。

## 2.4 GHz 电量查询的静态证据

以下 RVA 基于上述 SHA-256 对应的 32 位 DLL，首选基址为 `0x10000000`。这些是静态事实，尚不是针对当前接收器的实机测试结果。

| DLL / 函数 | RVA | 观察到的行为 |
| --- | --- | --- |
| RgDeviceManage / `RgHidDevice::HidRead24GPowerInfo` | 0x2BCD0 | 调用 GetDataFromDevice，命令为 0x30，偏移为 0 |
| `RgHidDevice::On24GDevicePowerTime` | 0x2B740 | 请求 10 字节数据；取前两字节扩展成两个 WORD 后发出电量信息信号 |
| `RgHidDevice::GetDataFromDevice` | 0x2BE60 | 组装 64 字节 AA 查询帧，收到成功回复后从回复 byte 8 复制数据 |
| `RgHidDevice::HidWriteStart` / `HidWriteEnd` | 0x2B7C0 / 0x2B8C0 | 官方读数据通路会调用 AA10 / AA11 起止步骤；其设备侧副作用仍需核实，不能仅由函数名认定为无副作用 |
| `RgHidDevice::SendFrameDataToDevice` | 0x2C180 | 选择有线或无线 CHidMessage 对象；回复 byte 7 等于 0x0F 或 0xFE 时返回错误 |

| `RgHidDevice::HidGet24GDeviceLink` | 0x2BCF0 | 发送 AA55；回复 byte 7 为 0x0F / 0xFE 时未知或失败，否则 byte 8 非零表示链路标志 |

GetDataFromDevice 的逻辑查询帧为：

```text
byte 0     AA
byte 1     查询命令（电量为 30）
byte 2..3  数据偏移，little endian（电量为 0）
byte 4     请求本块长度（电量请求 10 字节）
byte 5..6  16-bit sum，little endian
byte 7     0
byte 8..63 0（读请求）
```

校验和的静态算法是先将 byte 5 / 6 清零，再累加 byte 1..63，不包括 AA。官方驱动从回复 byte 8 取电量、byte 9 取第二状态字段；官方 UI 将第二字段解释为充电，但下文固件交叉检查发现语义冲突，因此产品不采用该充电解释。这不是社区 20 字节 13/4A 报文，不能混用字段或校验算法。

原生驱动固件中找到与 DLL 相互吻合的实现，以下地址是文件偏移 / 以零为基址的 Thumb 地址：

- `0x9904` 开始处理 64 字节帧；`0x9934` 检查首字节为 AA，`0x9950` 检查请求数据长度不超过 0x38。

- 成功收尾 `0xA094` 将回复 byte 7 设为 0x55 并发送 64 字节回复；错误路径设为 0x0F。
- 成功收尾没有对修改后的负载重新计算 byte 5 / 6，故不能给回复强加一个未实现的请求校验和规则。

### 原生百分比的 ADC 来源及有线调度

针对实机有线 AA30 返回 100 的语义，继续追踪了 `0x200000CC` 的全部直接字面地址引用。它不是一个仅因 USB 接入就固定为 100 的占位字段：

- ADC 采集函数 `0x152C` 从外设 `0x40012400 + 0x50` 读取采样值，存入 `0x20002EB8` 的 10 个半字样本。`0x1436` 去除最大 / 最小样本后计算均值。
- 启动采样路径 `0x9540` 与持续采样路径 `0x93C4` 都按 ADC 阈值换算百分比：不高于 `0x76C` 为 0，不低于 `0xA1E` 为 100，中间为 `(ADC - 0x76C) * 100 / 0x2B2`。结果经过 `0x200000F1 / F2` 状态及计数平滑后，在 `0x95E0` / `0x94FE` 写入 `0x200000CC`。
- GPIO 充满分支 `0x15DE..0x1616` 可将同一字段饱和为 100；这属于设备的满电估算逻辑，不表示精密容量测量。没有发现单纯检测 USB 模式就将百分比设为 100 的分支。
- 主循环 `0xC61E..0xC76C` 在节拍 `0x2000006D` 为真时，于 `0xC64E` 无条件调用 ADC 函数 `0x152C`。随后 `0xC6CC` 才检查模式 `0x200000D0 == 2` 并进入 USB 接收，在 `0xC6F0` 调用 AA 帧处理 `0x9904`。因此有线模式没有绕过 ADC 调度。
- 节拍源是定时器 `0x40001000` 中断函数 `0x1C88`；计数到 10 时，`0x1D40..0x1D44` 将 `0x2000006D` 设为 1。此处未把节拍计数擅自换成某个秒数。

百分比是**设备固件根据电压采样估算并维护的报告值**，主机成功读取的时间是取得该报告值的时间；无法由这个协议恢复设备内部 ADC 每一批的精确采样时间。实机运行固件未做完整读回比对，静态结论限定于上表指定 SHA-256 的官方原生 BIN，并与实际 AA 查询成功交叉印证。

### 第二状态字节的冲突

AA30 的 byte 9 取自 `0x20000290 + 0x10`。但在 `0x9540` 的启动采样路径和 `0x93C4` 的持续采样路径中，ADC 长期低于阈值会使这个字节置 1，例如 `0x9590..0x9594`、`0x9472..0x9476`；充满分支 `0x15F4..0x15F8` 将它清零。相反，GPIO 判定的 0 / 1 / 2 状态保存在 `0x20000290 + 0x14`，例如 `0x15C8..0x15DC`、初始化 `0x97A0..0x97BA`，AA30 并未复制该地址。

这足以否定把此 BIN 的 byte 9 无条件当作充电状态。可能存在驱动 / 固件修订不一致；没有对应运行固件的进一步证据时，不选择其中一套解释。生产解码现对所有 byte 9 取值返回 `ChargingState.Unknown`，原始状态值写入 Source 诊断。实际返回 `100 / 00` 因此展示为 **100%、充电未知**。

VIA 固件使用不同代码布局。初始立即数定位未找到 AA30；随后继续追踪了实际 raw HID 接收回调、命令分发、灯光扩展及电量灯显示路径，具体见下节。原生固件的 RAM 地址和分支不能移用到 VIA 固件，更不能据此给 36B0:3002 或 3554:FA09 发命令。

静态分析脚本：`research/zen65-local/thumb.py`，依赖同目录 tools 下的 Capstone，仅读取文件。协议分支与配置身份的证据已交给 hardware agent 继续核对实际硬件。

## VIA 固件的 raw HID 与电量变量追踪

对上述 SHA-256 为 F94C...176D 的 72,848 字节官方 BIN，继续做了有界的静态调用链检查。

### raw HID 回调与命令分发

`0xB99C` 从 raw USB 接收队列（RAM `0x20001288`）取 32 字节，将数据及长度 0x20 传给 `0xAF90`。`0xAF90` 最先调用前置钩子 `0xAEAA`，该钩子在这个具体 BIN 中固定返回 0，随后进入 VIA 分发。正常回复通过 `0xB988` 发送；该函数明确要求长度为 0x20，选择 raw HID 的发送通路。

`0xAFB4` 是 21 项 byte 跳转表，辅助例程 `0x1F0` 将每个表值乘 2 加到表首返回地址。复现可用 `thumb.py <BIN> --switch8 0xafb4 21 1`。

| VIA 命令 | 分支地址 | 静态行为 |
| --- | --- | --- |
| 01 | 0xAFD6 | 返回协议版本 00 0C |
| 02 | 0xAFE8 | get keyboard value；子选择 1 为运行时间、2 为布局选项、3 为矩阵状态、4 返回四个零字节 |
| 03 | 0xB044 | 设置 keyboard value；不能作为电量探测 |
| 04 / 05 / 06 | 0xB072 / 0xB07E / 0xB096 | 动态按键映射读取 / 写入 / 重置 |
| 07 / 08 / 09 | 0xB09C | custom value 分发；此 BIN 仅实现 channel 3 的 RGB 灯光值 |
| 0A / 0B | 0xAFD0 | 写入 FF，未处理 |
| 0C / 0D | 0xB0A6 / 0xB0AE | 宏数量 / 宏缓冲长度 |
| 0E / 0F / 10 | 0xB0BA / 0xB0D0 / 0xB0E6 | 宏缓冲读取 / 写入 / 重置 |
| 11 | 0xB0EC | 键位层数量 |
| 12 / 13 | 0xB0F2 / 0xB108 | 动态键位缓冲读取 / 写入 |
| 14 / 15 | 0xB11E / 0xB130 | 编码器映射读取 / 写入 |
| BB | 0xB14E → 0x2D4C | 将输入原样转发给无线侧通信缓冲；不是已证实的只读状态命令 |
| 其他 | 0xAFD0 | 写入 FF，未处理 |

custom value 的 channel 3 经 `0xAF50`，读取命令 08 经 `0xAEAE` 访问 RGB 状态 RAM `0x20002C00` 的亮度 / 效果 / 色彩参数；其他 channel 经 `0xAEA4` 将命令写成 FF。未将这些灯光参数当成电量。

BB 分支是必须保留的不确定点：`0x2D4C` 在内部条件允许时直接复制输入到无线发送缓冲，并触发无线侧发送。对应回复通路 `0x2510` 会将无线侧数据改头为 BB 后通过 raw HID 发回。它能转发什么、目标接收器允许哪些命令、是否有其他副作用，还缺该无线芯片 / 接收器的协议证据；不能因存在这条桥接就构造电量请求。

### 百分比 RAM 与电量灯显示

另定位到电量 RAM 字节 **`0x20000C6B`**（结构基址 `0x20000C68 + 3`）：

- `0x4500` 处理 10 个 ADC 样本，移除极值后按阈值换算 0～100，在 `0x45C6` 更新该字节。另一个充电分支在 `0x4642` 将满电值 100 写入相同字节。
- `0x328E` 读取该字节除以 10，用十段灯条显示；不超过 29 取红色，30～59 取黄色，至少 60 取绿色。这确认了其百分比语义。该显示函数由 `0x320C` 的显示模式进入，具体 Fn 组合的按键映射尚未在本次范围内完整关联，未将候选调用直接宣称为 Fn+Backspace。
- 内部发送分支 `0x2E04` 读取同一字节并放入无线侧消息 byte 3；该消息由 `0x2DB8` 形成内部前缀 0A / 40 及类型 10。这里是键盘向无线芯片的内部传输，未找到可以从主机以相同字节请求读取的证据。
- 在上述 raw HID 分发和已审查自定义值通道中，没有直接返回这个百分比 RAM 的专用分支。发现设备内部有准确电量变量，不等于证明主机 USB 接口提供该变量。

本次可以收窄结论：**该具体 VIA BIN 的标准 raw HID 命令分发与已实现 RGB 扩展没有专用电量读取；还存在未经解释的 BB 无线桥接，不能据此推断整个固件或其他版本绝无电量通路。** 此 BIN 的 USB 描述符身份 36B0:3025 与当前待调查 2.4 GHz 节点 36B0:3002 也不同，固件分析没有消除这种身份差异。

本节仅是静态分析结果。hardware agent 另行执行的标准 VIA version 查询、描述符读取和超时记录，见 `research/zen65/actual-via-version.json` 与 `actual-valuecaps.json`；不能将这些动作写成本子任务曾发送 AA / BB 命令，本子任务没有发送任何 HID 命令。

## 当前结论与下一步

用户接入有线后，hardware agent 记录到本机 **36B0:3025 / MI01 / FF60:0061 / IN65 OUT65**，Report ID 从实际 HID caps 取得。隔离 helper 使用已审查的 AA10 → AA30 → AA11，已于 2026-10-23 23:40（本机时区）成功读取 **100%、USB 已连接、充电未知**；原始状态字节为 00。原始记录在 `research/zen65/wired-read-result.json`。这次实测与合成协议 fixture 区分记录；fixture 仅验证解码边界，不能替代实测。

这证明该具体有线原生接口可读设备报告百分比；同 VID/PID 的 VIA IN33/OUT33 分支必须拒绝原生 AA 查询。官方配置中的无线 36B0:0001 尚无对应实机验证，用户当前的无线接收器 36B0:3002 仍未获得主机电量协议证据。唤醒后的有限 FF00 被动只读监听没有收到报告，不能据此推断永不主动上报，也不能给它发送改长 AA / BB / 4A 猜测命令。
